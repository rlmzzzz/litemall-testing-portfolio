## 一、为什么接口要用「按账号拆分」的 5 个集合？

这是本次实践中**最关键的一个坑**，面试时讲出来非常加分。

### 1.1 问题的现象

最初我把 36 个接口写在**一个** Postman 集合里，用 Newman 跑，结果**所有带 token 的用例全部返回 errno=506（无权限）**，包括本该全部通过的超管 admin123。

但在 Postman 界面里手动点，一个一个都通过。

### 1.2 排查过程

1. 先怀疑 token 没传过去 → 打印日志，发现 token 正常取到了。
2. 用 Python 脚本脱离 Newman 直接发请求（不带任何 cookie）→ **全部正确**。
   → 说明接口本身没问题，问题出在 Newman 的执行环境。
3. 对比差异：Postman 界面手工点是**一个请求一个请求**点；Newman 是**顺序跑完整个集合**。
4. 抓包看请求头 → 发现 Newman 发出的请求里除了 `X-Litemall-Admin-Token`，**还带了 `JSESSIONID` cookie**。

### 1.3 根因

```
登录接口 POST /admin/auth/login 的响应头里有 Set-Cookie: JSESSIONID=xxx
        ↓
Newman 默认维护一个 cookie jar（和浏览器一样），自动保存并在后续请求携带
        ↓
后端 Shiro 取身份时，【cookie 的优先级高于 token 请求头】
        ↓
集合里依次登录了 admin123 → mall123 → promotion123
        ↓
cookie 里的身份被最后一个登录的低权限账号 mall123 / promotion123 覆盖
        ↓
后面即使带上 admin123 的 token，后端仍按 cookie 里的低权限身份鉴权 → 506
```

一句话总结：**多账号共用一个集合时，Newman 的 cookie jar 会让后登录的低权限账号"顶掉"前面高权限账号的身份，而后端 cookie 鉴权优先于 token。**

### 1.4 解决方案（三选一，我选了第一种）

| 方案 | 做法 | 评价 |
|---|---|---|
| ✅ **按账号拆分集合** | admin123 / mall123 / promotion123 各自一个集合，单独跑 Newman | 最简单可靠，每个集合内 cookie 与 token 同账号，天然不冲突 |
| 方案二 | 每个请求前 `pm.cookies.jar().clear()` | 实测对 Newman 无效，jar 仍会写入 |
| 方案三 | 写请求级 pre-request 脚本删除 Cookie 头 | Postman 不允许删除自动携带的 cookie |

> 补充：集合 01（鉴权异常）里**故意不放任何成功登录**，这样连 cookie 都不会产生，用来纯净地验证"未登录/错误凭证是否被拦截"。

## 四、鉴权与参数边界实测基线

### 4.1 登录异常（errno 基线）

| 场景 | HTTP | errno | errmsg |
|---|---:|---:|---|
| 用户名不存在 | 200 | **605** | 用户帐号或密码不正确 |
| 密码错误 | 200 | **605** | 用户帐号或密码不正确 |
| 密码超长（200 字符） | 200 | 605 | 用户帐号或密码不正确 |
| 用户名为空 | 200 | **401** | 参数不对 |
| 密码为空 | 200 | **401** | 参数不对 |
| 两者均为空 | 200 | **401** | 参数不对 |
| 正确账号密码 | 200 | 0 | 成功 |

> 面试点：所有异常**HTTP 状态码都是 200**，业务结果靠 `errno` 区分。这是国内很多 Java 项目的常见设计——所以**接口断言不能只断言 HTTP 200，必须断言 errno**，否则等于没测。

### 4.2 未登录 / 无效凭证

| 场景 | errno | errmsg |
|---|---:|---|
| 未带 token | 501 | 请登录 |
| 错误 token | 501 | 请登录 |
| 空 token | 501 | 请登录 |

### 4.3 参数边界（admin123）

| 场景 | errno | 实测表现 | 判定 |
|---|---:|---|---|
| 商品详情 id 不存在（99999999） | **502** | 返回"系统内部错误" | ❌ **Bug-6**：应为 4xx 业务提示 |
| 商品详情 id=0 / id=-1 | **502** | 同"系统内部错误" | ❌ **Bug-6**：0 与负数走了同一个异常分支 |
| 商品详情 缺少 id | 402 | `arg0must not be null`（**英文 + `arg0` 后缺空格**） | ⚠️ Bug-6 附带问题：提示不规范 |
| 商品详情 id=abc / id=99999999999 | 402 | 参数值不对 | ✅ 符合预期 |
| 商品列表 page=abc | 402 | 参数不对 | ✅ 符合预期 |
| 商品列表 page=0 | 0 | 收敛为 `page=1`，响应回显 1 | ✅ 可接受 |
| 商品列表 **limit=0** | 0 | **返回 250 条（全量），共 1,514,715 字节** | ❌ **Bug-8**：分页失效 |
| 商品列表 **limit=10000** | 0 | **同样返回全量 250 条** | ⚠️ 归入 Bug-8：`limit` 无上限保护 |
| 商品列表 limit=-1 | 0 | 静默返回 0 条，`limit` 字段回显 -1 | ⚠️ 归入 Bug-8：非法值不报错、静默吞掉 |
| 商品列表 page=9999 | 0 | 返回第 50 页 5 条，但响应 `page` 字段回显 **50**，不等于请求值 9999 | ⚠️ 归入 Bug-8：参数被静默改写且不回告调用方 |
| 商品列表 中文搜索"手机" | 0 | 返回 3 条，名称均含"手机" | ✅ 符合预期 |

## 七、测试结论与风险评估

### 7.1 结论：**不通过**

存在 1 个**严重级越权缺陷**（Bug-7）未修复，建议修复后再进入下一阶段。

### 7.2 分维度结论

| 维度 | 结论 |
|---|---|
| 功能正确性 | 基本可用，admin123 正向业务 24 条用例中 22 条通过 |
| 鉴权（你是谁） | ✅ 全局生效，未登录一律 501 |
| **授权（你能干什么）** | ⚠️ **存在严重缺陷**：`/admin/dashboard` 越权（Bug-7）；其余 13 个接口拦截正常 |
| 参数校验 | 类型校验正常；**边界值处理不足**（limit=0 / 10000 / -1，Bug-8） |
| 数据安全 | ⚠️ 密码哈希随列表下发（Bug-9）；金额篡改经源码确认为不可行 ✅ |

### 7.3 风险清单与整改建议

| 缺陷 | 风险 | 建议整改方式 |
|---|---|---|
| **Bug-7** | 任意已登录账号都能读全站商品数、用户数、订单数——这是**经营数据**，且接口连 `@RequiresPermissions` 注解都没有 | 补 `@RequiresPermissions("dashboard:read")`，并在角色里显式授权 |
| **Bug-8** | `limit` 无上下限约束，单次可拉 1.5 MB；可被用于接口压测放大、爬取全量商品 | 服务端对 `limit` 强制约束（建议 1~100），超出即报 402 |
| **Bug-9** | BCrypt 哈希被下发；一旦响应被缓存/日志留存，等于给了离线爆破的材料 | 返回 DTO 而非数据库实体（`LitemallUser`），排除 `password` 字段 |
| **Bug-6** | 502 被前端和监控统一归为"服务端故障"，产生告警噪音，掩盖真实异常 | 查询结果为 null 时返回业务错误码（如 611 商品不存在） |

### 7.4 遗留 / 未覆盖项（明确说明边界，不掩盖）

| 未覆盖项 | 原因 | 后续计划 |
|---|---|---|
| 支付链路、下单并发与重复提交 | 需改造前端交互，Postman 覆盖不到"用户连点两次" | 转 Fiddler 弱网专项（`19-Fiddler抓包改包实战指南.md` 任务 3） |

## 九、面试怎么讲这一段（要点）

### 9.1 90 秒版本（建议背下来）

> "接口测试我用 Postman 做用例设计、Newman 做命令行执行，5 个集合、57 个请求、241 条断言，跑出 4 条失败断言，最后往禅道提了 4 个单。
>
> 过程中踩到一个比较典型的坑：多账号写在同一个集合里跑 Newman 时，所有带 token 的用例都返回 506 无权限，但手工在 Postman 里点又正常。排查下来是 Newman 的 cookie jar 保存了登录接口下发的 JSESSIONID，而后端 Shiro 里 cookie 鉴权的优先级高于 token 请求头，导致后登录的低权限账号把前面的身份顶掉了。解决办法是按账号拆成多个集合分别执行。
>
> 结果里最严重的一个是统计面板接口没做权限控制，低权限角色能越权读到全站商品数、用户数、订单数。这条我定位到了源码层面：`AdminDashbordController` 整个类没有 `@RequiresPermissions` 注解，而且我把全部 30 个 Controller 扫了一遍，只有它一个该有权限却完全没有。"

### 9.2 被追问时的四个展开点

| 追问 | 怎么答 |
|---|---|
| "断言 FAIL 是不是你脚本写错了？" | 断言是**按需求应有的正确行为**写的（如"无权限接口应返回 506"），FAIL 恰恰证明程序没做到。截图里同时给出实际响应体，能自证不是脚本问题 |
| "为什么用 `127.0.0.1` 不用 `localhost`？" | Postman / 浏览器在 `localhost` 下会带 `JSESSIONID` cookie，而 cookie 鉴权优先于 token，会让越权结论不可信。**换主机名是最快的凭证隔离手段** |
| "你怎么确定这个越权不是误报？" | 先调 `/admin/auth/info` 自证身份（返回 `name=mall123`、`perms` 只有 10 条 brand/category 权限），再证明这个身份拿到了 dashboard 数据 —— **我是谁 → 我有什么权限 → 我实际拿到了什么** |
| "有没有你发现了但没提的？" | 有。商品列表接口返回 `detail` 富文本字段、占全量响应 84.3%，但 `topic/list` 返回 `content`、`category/list` 返回 `children`，属项目一致的实现风格，单独立单会被判"设计如此"。我把它作为 Bug-8 的影响放大分析附上去，没单独开单 |

### 9.3 加分点

- 有量化数据：**57 请求 / 241 断言 / 4 失败 / 4 个缺陷单（禅道 #3~#6）**
- 能区分缺陷来源：**自动化跑出 3 个（Bug-6 / 7 / 8），人工复核补充 1 个（Bug-9）** —— 说明测试设计不依赖脚本
- 讲得出"HTTP 200 但 errno≠0"的业务码断言意识
- 讲得出 cookie 与 token 鉴权优先级的排查思路（体现真排查过，不是背的）
- 缺陷能落到源码层面（Bug-7 定位到 `AdminDashbordController` 缺 `@RequiresPermissions`）
