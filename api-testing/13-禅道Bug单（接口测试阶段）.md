## 0.2 标题规范

**公式：`【模块】+ 操作/接口 + 现象`**，40 字以内，必须能被搜索到。

三条硬规则：

1. 必须含**接口路径或功能名** —— 别人搜 `/admin/dashboard` 要能搜到你这条
2. 必须写**现象**，不写"有问题"
3. 不写主观词："很难用""感觉不对""建议优化"

对照：

| ❌ 不合格 | ✅ 合格 |
|---|---|
| 权限有问题 | 【系统管理】/admin/dashboard 未做权限校验，低权限角色可越权查看全站经营数据 |
| limit 传 0 有 bug | 【商品管理】/admin/goods/list 的 limit=0 时分页失效，一次返回全量 250 条 |
| 商品详情报错 | 【商品管理】/admin/goods/detail 查询不存在的商品 id 返回 502 系统内部错误 |
| 会员列表返回了密码 | 【用户管理】/admin/user/list 响应中返回会员密码哈希字段 password |

## 0.3 严重程度 × 优先级

**先分清这两栏的区别**（新手最容易混）：

- **严重程度** = 技术影响有多大（会不会坏数据、丢钱、泄密）
- **优先级** = 业务上多急着修（正常用户能不能撞上）

| 严重程度 | 判定标准 |
|---|---|
| 致命 | 系统崩溃、数据丢失、金额算错、**可越权访问他人数据** |
| 严重 | 主要功能不可用、**校验缺失导致数据泄露或脏数据** |
| 一般 | 次要功能异常、错误提示不友好、性能问题 |
| 建议 | 文案、体验、优化建议 |

### ⚠️ 禅道里的真实取值是数字，别填错

禅道 22.5 的界面**只显示数字 1/2/3/4，不显示"严重/一般"这类文字标签**。映射如下（优先级部分为禅道语言包原文：**`1 是最高优先级，4 是最低优先级`**）：

| 显示数字 | 严重程度 severity | 优先级 pri |
|:---:|---|---|
| **1** | 致命 | 最高 |
| **2** | 严重 | 高 |
| **3** | 一般 | 中 |
| **4** | 轻微 | 低 |

**记忆要点：两者都是"数字越小越严重"。** `pri=1` 最急，`severity=1` 最致命。

> 这是个真踩过的坑：第一遍把"高"填成 `1`、"中"填成 `2`，等于**把 4 个单的优先级整体抬高了一档**。
> 因为这个项目里 `admin123` 是唯一测试账号，界面只有数字，光看界面根本发现不了 —— **必须回源码语言包确认**。
> 方法论：**当工具界面不告诉你取值含义时，去工具自己的配置/语言包里找，不要猜。**

**判定三问**：

1. 会不会造成**数据 / 资金 / 隐私**损失？→ 至少"严重"
2. **正常用户走正常路径**会不会撞上？→ 会则优先级高，不会则中/低
3. 有没有**绕过办法**（用户能自己避开）？→ 有则严重程度可降一级

**本次 4 单的取值与理由**（保证不出现"致命+低"这类矛盾组合）：

| 单号 | 严重程度 | **severity** | 优先级 | **pri** | 理由 |
|---|:---:|:---:|:---:|:---:|---|
| **Bug-7** | 严重 | **2** | 高 | **2** | 越权读到全站经营数据，安全类；任何已登录账号都能撞上 |
| **Bug-8** | 一般 | **3** | 中 | **3** | 正常前端只传 10/20/50，需构造参数才能触发；但一旦触发就是全表外泄 1.5 MB |
| **Bug-9** | 一般 | **3** | 中 | **3** | 泄露的是不可逆哈希、且需管理员权限，实际风险有限；但字段本身不该下发 |
| **Bug-6** | 一般 | **3** | 中 | **3** | 属提示不友好，不影响数据正确性 |

> 自检口径：**severity 和 pri 的数字不要差太多**。差 2 档以上（比如"致命 + 低"）就要能说清理由，否则评审一定问。

> 原则：**宁可保守，但理由要能说出口。** 面试官看的是判断依据，不是级别高低。

## 0.4 正文四段式

**必写四段**（顺序固定）：

```
【前置条件】
【复现步骤】
【预期结果】
【实际结果】
```

**选写两段**（写了加分）：

```
【影响范围】  ← 什么场景下用户会撞上
【定位分析】  ← 文件 + 方法 + 缺什么（开发参考，不要当成"教开发写代码"）
```

规范细则：

- **复现步骤**：编号列表，**每一步只有一个动作**，含完整 URL / 参数 / 账号，别人照着做能 100% 复现
- **实际结果**：贴**原始响应**，不要转述（"返回了错误" ❌ / `{"errno":502,"errmsg":"系统内部错误"}` ✅）
- **预期结果**：必须给**依据**（接口文档 / 业务语义 / 同类接口对比）。**没有依据的"我觉得"不算 Bug**
- **定位分析**：写清哪个文件、哪个方法、缺什么注解或判空 —— 这是从"会用工具"到"懂系统"的分水岭

**依据只有三种来源**：

| 依据类型 | 例子 |
|---|---|
| ① 接口文档 | `doc/admin.md` 写明 `limit` 默认值 10 → 正常取值为正整数 |
| ② 业务语义 | "每页条数"填 0 / 负数没有业务含义 |
| ③ 对比法 | 同一系统内 `limit=abc` 返回 402，说明有参数校验机制，只是漏了边界值 |

## 0.5 附件规范：截图里必须有什么

一张合格的复现截图，**五样缺一不可**：

1. 完整 URL（域名 + 路径 + Query 参数）
2. **请求头 `X-Litemall-Admin-Token` 那一行** ← 越权单没有它就等于没有证据
3. 请求体 / 参数
4. 响应体全文（含 `errno`）
5. 断言结果（Postman `Test Results` 或 Newman 报告）

## 0.6 提单前 8 条自检

```
□ 1. 我是以「谁」的身份发的这个请求？（先用 /admin/auth/info 自证）
□ 2. cookie 关了吗？（Postman → Settings → General → 取消 Send cookies）
□ 3. 这个现象能重复出现吗？（同一操作连做 3 次）
□ 4. 预期结果的依据是什么？（说不出依据 → 先别提）
□ 5. 这条单里只有一个现象吗？
□ 6. 严重程度和优先级矛盾吗？
□ 7. 标题里有接口路径吗？
□ 8. 附件齐了吗（URL / Header / 响应 / 断言 四件套）？
```

2. 同一账号访问其它 13 个无权限接口**全部正确返回 506**，说明系统的细粒度权限校验机制本身是正常工作的

## 【影响范围】

- 后台任意一个已登录账号（哪怕权限最小）都能读取全站经营数据
- 前端侧边栏不显示"统计面板"菜单**只是隐藏入口，不构成防护**：用 Postman / 浏览器直连接口即可获取
- 属于**纵向越权（权限提升/敏感信息泄露）**，按等保与常见安全基线应判定为缺陷

## 【定位分析】

`litemall-admin-api/src/main/java/org/linlinjava/litemall/admin/web/AdminDashbordController.java` 第 19-35 行：

```java
@RestController
@RequestMapping("/admin/dashboard")
@Validated
public class AdminDashbordController {          // ← 类上无 @RequiresPermissions
    ...
    @GetMapping("")
    public Object info() {                       // ← 方法上也无 @RequiresPermissions
        int userTotal = userService.count();
        ...
```

对照正常写法 `AdminBrandController.java`：

```java
@RequiresPermissions("admin:brand:list")         // ← 有权限注解
@RequiresPermissionsDesc(menu = {"商场管理", "品牌管理"}, button = "查询")
@GetMapping("/list")
public Object list(...) { ... }
```

**结论：`/admin/dashboard` 未添加 `@RequiresPermissions` 注解，Shiro 不执行权限校验，任何已登录用户均可访问。**

**建议修复**：为 `info()` 方法补充 `@RequiresPermissions("admin:dashboard:list")` 及对应的 `@RequiresPermissionsDesc`。

## 【系统性排查（附录，证明非偶发）】

对 `litemall-admin-api` 全部 **30 个 Controller** 做静态扫描，统计 `@RequiresPermissions` 注解数量：

| Controller | 路径 | 注解数 | 定性 |
|---|---|---:|---|
| AdminAuthController | `/admin/auth` | 0 | ✅ 合理（登录/登出/验证码本身不能要求权限） |
| AdminProfileController | `/admin/profile` | 0 | ✅ 合理（有 `@RequiresAuthentication`，只返回自己的数据） |
| AdminRegionController | `/admin/region` | 0 | ⚠️ 可接受（省市区基础数据，非敏感） |
| **AdminDashbordController** | **`/admin/dashboard`** | **0** | ❌ **本缺陷** |
| 其余 26 个 Controller | — | 1~8 | ✅ 均已配置权限注解 |

**30 个里只有 4 个没上权限锁，3 个有合理解释，剩下这 1 个就是本缺陷。**

补充：4 个无权限注解的接口在**不带任何凭证**时均返回 `{"errno":501,"errmsg":"请登录"}`（实测），
说明**登录校验是全局生效的**，缺的只是**细粒度权限校验**。

```
2. 已用 admin123 / admin123 登录并取得 token（POST /admin/auth/login）

【复现步骤】
1. 请求商品列表，分页参数 limit 设为 0
   GET http://127.0.0.1:8080/admin/goods/list?page=1&limit=0
   请求头：X-Litemall-Admin-Token: <TOKEN>

2. 观察响应体中 data.list 的条数、以及响应体总大小

3. 【对照实验】把 limit 换成其它值再请求同一接口
   GET http://127.0.0.1:8080/admin/goods/list?page=1&limit=5
   GET http://127.0.0.1:8080/admin/goods/list?page=1&limit=-1
   GET http://127.0.0.1:8080/admin/goods/list?page=1&limit=abc
   GET http://127.0.0.1:8080/admin/goods/list?page=1&limit=10000
   GET http://127.0.0.1:8080/admin/goods/list?page=9999&limit=5
```

## 【实际结果】

| 请求 | errno | 返回条数 | `page` 回显 | `limit` 回显 | `pages` 回显 | 响应体大小 |
|---|---:|---:|---:|---:|---:|---:|
| `page=1&limit=5` | 0 | 5 | 1 | 5 | 50 | 1,813 字节 |
| **`page=1&limit=0`** | **0** | **250（全表）** | **0** | 0 | 0 | **1,514,715 字节（1.5 MB）** |
| `page=1&limit=-1` | 0 | 0 | 0 | -1 | 0 | 90 字节 |
| `page=1&limit=abc` | 402 | — | — | — | — | 40 字节（`参数值不对`）✅ |
| `page=1&limit=10000` | 0 | 250 | 1 | 10000 | 1 | 1,514,719 字节 |
| `page=9999&limit=5` | 0 | 5 | **50** | 5 | 50 | 42,821 字节 |

**关键点：请求写的是 `page=1`，响应回显的却是 `page=0`；`limit=0` 时 `pages` 也回显为 0。响应中的分页字段与请求不一致。**

## 【预期结果】

`limit=0` 属于非法分页参数，应满足以下任一（本次建议第 1 种）：

1. 返回参数错误：`{"errno":402,"errmsg":"参数值不对"}`
2. 按语义返回 0 条数据（`list` 为空数组）

**不应返回全量 250 条数据。**

**依据（三条）**：

1. **业务语义**：`limit` = 每页条数，取值为 0 或负数没有业务含义
2. **接口文档 / 源码**：`AdminGoodsController.list()` 中 `@RequestParam(defaultValue = "10") Integer limit`，默认值 10 说明正常取值为正整数
3. **内部对比法**：同一接口传 `limit=abc` 能正确返回 `402 参数值不对`，说明系统本身有参数校验机制 —— **只是漏掉了数值边界**（0 / 负数 / 超大值）

**附带问题（同一成因，建议一并修复）**：

- `limit=10000` 无上限保护，同样返回全量 250 条
- `page=9999` 时越界页被**静默收敛**为第 50 页，但响应中 `page` 字段回显 50 而非请求的 9999 —— 调用方无法感知自己的参数被改写了

## 【影响范围】

- 单次请求返回全表数据，商品量增长后带来明显的**性能与内存压力**（当前 250 条已 1.5 MB，1 万条商品时约 60 MB）
- 若上游（前端 / 第三方调用方 / 脚本）传入未校验的分页值，会触发**大结果集响应**，极端情况下可被用于**接口层资源消耗攻击**

## 【定位分析】

`litemall-admin-api/.../web/AdminGoodsController.java` 的 `list()` 方法：

```java
@RequiresPermissions("admin:goods:list")
@GetMapping("/list")
public Object list(..., @RequestParam(defaultValue = "10") Integer limit, ...)
```

`limit` 仅提供了默认值 10，**未做取值范围校验**，直接透传给分页组件；当 `limit=0` 时未启用分页，导致全表返回。

**建议修复**：在 Controller 或 Service 层统一做分页参数边界校验，例如 `limit` 限制在 1~100，`page` 限制为 ≥1，非法值返回 `errno=402`。

## 【为什么这 1.5 MB 这么大（影响放大分析）】

同一接口 `page=1&limit=5` 只返回 1,813 字节，`limit=0` 却返回 1,514,715 字节。逐字段拆解：

| 组成部分 | 体积 | 占比 |
|---|---:|---:|
| 全部字段合计 | 1,509,453 字节（约 6,038 字节/条） | — |
| **其中 `detail` 字段**（商品详情富文本） | **1,276,650 字节**（平均 5,107 字符/条） | **占响应体 84.3%** |
| 去掉 `detail` 后 | 183,973 字节（约 736 字节/条） | 12.2% |

**列表接口返回的每条记录里，84% 的体积是一个列表页根本不会展示的富文本字段。**

同参数不同页的对比更能说明问题：

| 请求 | 响应大小 |
|---|---:|
| `page=1&limit=5` | 1,813 字节 |
| `page=50&limit=5` | 42,821 字节（**23.6 倍**） |

同样是 5 条数据，差 23 倍，差异全部来自 `detail` 字段的内容（前 5 条商品详情为空，第 50 页的 5 条都有富文本详情）。

> ⚠️ **本项不单独提单，理由见第六章。** 但它是 Bug-8 危害被放大 8 倍的直接原因，作为附件数据一并提交。

## 【预期结果】

会员列表接口的响应中**不应包含 `password` 字段**（行业惯例：密码等凭据类字段永不下发到任何响应体，包括接口层与日志）。

**依据（两条）**：

1. **业务语义**：会员列表页只需要 `id / username / nickname / mobile / avatar / status / addTime`，密码哈希对任何业务逻辑都无用
2. **最小权限原则 / 数据最小化**：接口应只返回调用方需要的数据；密码哈希属凭据类敏感数据

## 【影响范围】

- 管理员账号被窃取 / 会话被劫持后，可批量拉取全量会员密码哈希，用于**离线暴力破解**
- 哈希一旦外泄无法撤回（会员改密码前的历史泄露永久存在）
- 响应体与前端日志、浏览器缓存、代理日志中会留下哈希副本

## 【定位分析】

`litemall-admin-api/.../web/AdminUserController.java` 第 36-44 行：

```java
@GetMapping("/list")
public Object list(String username, String mobile, ...) {
    List<LitemallUser> userList = userService.querySelective(username, mobile, page, limit, sort, order);
    return ResponseUtil.okList(userList);       // ← 直接返回数据库实体 LitemallUser
}
```

**直接把数据库实体 `LitemallUser`（对应表 `litemall_user`）作为响应返回**，实体里有什么字段就下发什么字段，因此 `password` / `sessionKey` 一并被序列化。

**建议修复**：

1. 在 `LitemallUser` 的 `password` / `sessionKey` 字段上加 `@JsonIgnore`（最小改动）
2. 或改用 VO（`UserVo`）只输出列表页需要的字段（推荐，同时解决 Bug-8 同类的"字段冗余"问题）
3. 对 `password` / `sessionKey` 等字段做统一脱敏，避免同类问题在其它接口复现

| **优先级** | 中（pri=**3**） |
| **操作系统** | Windows 11（os=win11） |
| **浏览器** | （留空）接口层复现 |
| **禅道 Bug ID** | **#6**（已提交） |

## 正文

```
【前置条件】
1. 后端已启动：http://127.0.0.1:8080
2. 已用 admin123 / admin123 登录并取得 token

【复现步骤】
1. 请求一个数据库中确定不存在的商品 id
   GET http://127.0.0.1:8080/admin/goods/detail?id=99999999
   请求头：X-Litemall-Admin-Token: <TOKEN>

2. 观察响应的 errno 与 errmsg

3. 【对照实验】把 id 换成其它取值再请求
   GET http://127.0.0.1:8080/admin/goods/detail?id=0
   GET http://127.0.0.1:8080/admin/goods/detail?id=-1
   GET http://127.0.0.1:8080/admin/goods/detail?id=99999999999
   GET http://127.0.0.1:8080/admin/goods/detail?id=abc
   GET http://127.0.0.1:8080/admin/goods/detail?id=1181009
   GET http://127.0.0.1:8080/admin/goods/detail        （不传 id）
```

## 【实际结果】

| 请求 | errno | errmsg | 判定 |
|---|---:|---|---|
| `id=99999999`（合法但不存在） | **502** | 系统内部错误 | ❌ 本缺陷 |
| `id=0` | **502** | 系统内部错误 | ❌ 本缺陷 |
| `id=-1` | **502** | 系统内部错误 | ❌ 本缺陷 |
| `id=99999999999`（超出 int 范围） | 402 | 参数值不对 | ✅ 正确 |
| `id=abc`（类型非法） | 402 | 参数值不对 | ✅ 正确 |
| `id=1181009`（存在） | 0 | 成功 | ✅ 正确 |
| 不传 `id` | 402 | **arg0must not be null** | ⚠️ 见下方附带问题 |

## 【预期结果】

"商品不存在"属于**可预期的业务场景**，不是系统异常，应返回业务错误码与中文提示：

```json
{"errno":611,"errmsg":"商品不存在"}
```

**依据（两条）**：

1. **业务语义**：查询一个不存在的 id 是正常业务路径（用户手输 URL、商品被删除后书签失效），不是系统故障，不应报"系统内部错误"
2. **对比法**：同一接口的其它非法输入（`id=abc`、`id=99999999999`、不传 id）**都能正确返回 402 并给出提示**，说明该接口本身有参数校验；唯独"ID 合法但查不到记录"走到了 502，说明是**查询结果为 null 后未判空**导致的

**附带问题（建议一并修，不单独提单）**：不传 `id` 时 `errmsg` 返回 `arg0must not be null` ——
① 是英文；② `arg0` 与 `must` 之间缺空格，明显是拼接错误。属于**提示信息不规范**，用户看不懂。

## 【影响范围】

- 用户在前端打开一个已删除的商品详情页时，会看到"系统内部错误"，无法区分是"商品没了"还是"系统坏了"
- 502 会被前端与监控统一归类为**服务端故障**，造成告警噪音，掩盖真实的服务端异常

## 【定位分析】

`litemall-admin-api/.../web/AdminGoodsController.java` 第 102-106 行：

```java
@RequiresPermissions("admin:goods:read")
@RequiresPermissionsDesc(menu = {"商品管理", "商品管理"}, button = "详情")
@GetMapping("/detail")
public Object detail(@NotNull Integer id) {
    return adminGoodsService.detail(id);        // ← 未判空，null 继续往下走
}
```

Service 查询返回 `null` 后未判空即被后续逻辑取值，触发空指针，被全局异常处理器兜底成 502。

**建议修复**：

```java
if (goods == null) {
    return ResponseUtil.fail(GOODS_NOT_EXIST, "商品不存在");
}
```

# 四点五、用禅道 API 批量提单（本次实际用的方式）

**为什么值得掌握**：手填 4 个单要 20 分钟，且容易漏字段、填错级别。API 提单可复用、可校验、可批量。

## 认证：两层，缺一不可

```bash
# 第 1 层：外层 Apache Basic 认证（浏览器打开禅道时那个弹窗）
Authorization: Basic base64("zentao:123456")

# 第 2 层：换 token
POST http://127.0.0.1/zentao/api.php/v1/tokens
Body: {"account":"admin","password":"<密码>"}
→ 201 {"token":"7c95bbab08f83f5f67d39ee8fa9fe1f7"}

# 之后所有请求带
Token: <上一步的 token>
```

> 少了 `Authorization: Basic` 会直接被 Apache 挡在门外，**根本到不了禅道**，报的还是 401 —— 容易误判成"密码错了"。

|---|---|

# 六、提完之后：禅道 Bug 生命周期怎么走

提单只是第一步，**走完一个完整生命周期**才算真正掌握缺陷管理（阶段四的完成标志里也写了这条）。

| 阶段 | 谁操作 | 你要做的事 |
|---|---|---|
| 新建 | 你 | 提交 4 个单，状态为「激活」 |
| 确认 | 开发 | 开发确认后状态变「已确认」；若被打回，见第七章 |
| 已解决 | 开发 | 开发填「解决方案」+「解决版本」，状态变「已解决」 |
| **验证** | **你** | **按原复现步骤重跑一遍**，确认问题真的没了 |
| 关闭 | 你 | 验证通过 → 「关闭」；未通过 → 「激活」（必须写清哪一步仍失败） |
| 重新激活 | 你 | 附上新证据 + `解决版本`，直接「激活」，**不要另开新单** |

**验证环节的三个规范**（这是新手最常做错的地方）：

1. **必须按原步骤重跑，不能凭感觉说"应该好了"**
2. 验证不通过时，**要写明是在哪一步、返回了什么**，不能只写"还是不行"
3. **回归验证要覆盖相邻场景**：比如 Bug-8 修了 `limit=0`，要顺手验证 `limit=-1`、`limit=10000`、`page=9999` 是否一并处理了

# 七、开发打回你单子的 7 种理由，与提前规避的方法

| 打回理由 | 真实含义 | 怎么提前堵住 |
|---|---|---|
| "我复现不了" | 你的步骤缺关键前置条件 | 复现步骤写全 URL + 参数 + 请求头 + 账号；前置条件写清 cookie 设置 |
| "设计如此" | 你给不出"预期"的依据 | 【预期结果】必须附依据（接口文档 / 业务语义 / 对比法） |
| "正常用户不会这么操作" | 你的输入太"人为" | 在【影响范围】里说明什么真实场景会撞上；用 Fiddler 断点改包，证明是"在真实请求上改了一个数" |
| "这是前端的问题" | 责任边界 | 附接口层原始响应（Postman/Newman），证明**绕过前端直接请求服务端也是这个结果** |
| "环境问题，我本地是好的" | 环境差异 | 附上版本号 `影响版本 v1.0.0` 与完整请求响应；必要时附 `docker ps` 输出 |
| "优先级没那么高" | 你把 P4 提成了 P2 | 用 0.3 的判定三问，写清定级理由 |
| "这条我改不了，是框架限制" | 确实改不动 | 接受他的解释，但要求在单里写清「不修复原因」，而不是直接关单 |

## 关于"列表接口返回 `detail` 大字段"为什么**没有**单独提单

这是本次一个刻意做的判断，理由比结论更重要：

我把同类接口都拉出来比了一遍（`page=1&limit=5`）：

| 接口 | 单条记录体积 | 是否含"详情类"大字段 |
|---|---:|---|
| `/admin/brand/list` | 304 字节 | 无 |
| `/admin/user/list` | 397 字节 | 无 |
| **`/admin/goods/list`** | **398 字节（`detail` 为空时）/ 约 6,038 字节（含 detail）** | **含 `detail`** |
| `/admin/category/list` | 2,834 字节 | 含嵌套 `children` 树 |
| `/admin/topic/list` | 850 字节 | 含 `content` 富文本 |

**`goods` 有 `detail`、`topic` 有 `content`、`category` 有 `children` —— 这是项目里一致的实现风格，属于"设计选择"，不是"实现缺陷"。**

把它单独立单，大概率会被回一句"设计如此/原有架构就是这样"，反而消耗你的提单信誉。

**但它的数据照样有用**：作为 Bug-8 的【影响放大分析】附件——**正因为列表里带了 84% 体积的 `detail`，`limit=0` 才会从"多返回几条"变成"1.5 MB 响应"**。

> 这就是"发现疑点"和"判定缺陷"的分界线：
> **发现疑点靠攻击点清单；判定缺陷靠依据和一致性对比。**
> 面试里讲这个判断过程，比多提一个 Bug 值钱。
