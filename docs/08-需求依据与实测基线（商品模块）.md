## 一、先纠正我之前的错误（改了两次，第二次才是真的）

### 第一次纠正（错的方向）

我写「价格填 -1 应该提示不能为负」→ 实测看到 `401 参数不对` → 我判定**已拦截，不是 Bug**。

### 第二次纠正（真相）

那个 401 **根本不是价格触发的，是库存触发的**。因为我当时把「价格 -1」和「库存 -5」写在同一个用例里了，**一次改了两个变量，却把结果归给了其中一个**。

重新做单变量对照实验后（见 4.2 节），真相是：

| 场景 | 结果 |
|---|---|
| 库存 = -5，价格正常 | `401 参数不对` → **已拦截** ✅ |
| 价格 = -1，库存正常 | `errno:0 成功` → **入库 -1.00** ❌ **是 Bug** |
| 专柜价 = -1，其余正常 | `errno:0 成功` → **入库 -1.00** ❌ **是 Bug** |

也就是说：**库存有校验，价格一点校验都没有。** 而且这个 Bug 你自己已经亲手造出来了——你在后台新增的「手机」商品，`counter_price` 就是 `-1.00`。

### 教训（比 Bug 本身重要得多）

**做对照实验，一次只能改一个变量。**

我那次是 `{"counterPrice": -1, "products":[{"price": -1, "number": -5}]}` —— 价格、库存同时改，结果返回 401，我就想当然地归给了价格。**如果我拿这个结论去提 Bug，开发一查代码就会驳回。**

这正好印证了第一节想说的：不光「我觉得应该怎样」不能信，**连「我实测出来的」如果实验设计有问题，也一样是错的**。

## 三、本模块的系统真实规则

### 3.1 前端校验（`create.vue` 第 369-372 行）——只有两条

```js
rules: {
  goodsSn: [{ required: true, message: '商品编号不能为空', trigger: 'blur' }],
  name:    [{ required: true, message: '商品名称不能为空', trigger: 'blur' }]
}
```

**价格、库存、名称长度、编号唯一性 —— 前端一律不校验。** 这就是 Bug 的温床。

### 3.2 后端校验（`AdminGoodsService.java` 第 243-246 行）

```java
String name = goods.getName();
if (goodsService.checkExistByName(name)) {
    return ResponseUtil.fail(GOODS_NAME_EXIST, "商品名已经存在");
}
```

- 只做**商品名查重**（`andNameEqualTo`）
- **不校验商品编号是否重复**
- **不校验名称长度、是否为空白字符、是否 trim**
- 价格/库存由参数绑定阶段拦截（负数/字母 → 401 / 402）

### 3.3 数据库约束（`DESC litemall_goods`）

| 字段 | 类型 | 约束 |
|---|---|---|
| `goods_sn` | varchar(63) | **NOT NULL，仅有普通索引（MUL），非唯一** |
| `name` | varchar(127) | NOT NULL，无唯一约束 |
| `counter_price` / `retail_price` | decimal(10,2) | 可为 NULL |
| MySQL `sql_mode` | 含 `STRICT_TRANS_TABLES` | 超长直接报错，不截断 |

> `sql_mode` 有 `STRICT_TRANS_TABLES` → 名称超过 127 字符会抛异常，而不是被静默截断。

## 四、实测结果（真实请求 + 落库核对）

| 编号 | 输入 | 接口返回 | 落库结果 | 判定 |
|---|---|---|---|---|
| A | 正常数据 | `errno:0 成功` | 正常 | ✅ 通过 |
| B | 名称 = 单个空格 | `errno:611 商品名已经存在` | 未入库 | ⚠️ 见 Bug-3 |
| C | 价格 -1 **+** 库存 -5（双变量，结论作废） | `errno:401 参数不对` | 未入库 | ⚠️ 见 4.2 节重新拆分 |
| D | 名称 = 200 字符 | **`errno:502 系统内部错误`** | 未入库 | ❌ **Bug-2** |
| E | 价格 = `abc` | `errno:402 参数值不对` | 未入库 | ✅ 通过 |
| F | 编号重复（同 T001） | **`errno:0 成功`** | **两条记录，goods_sn 均为 T001** | ❌ **Bug-1** |
| G | 名称 = 制表符 `\t` | **`errno:0 成功`** | **入库为 `\t`** | ❌ **Bug-3** |
| H | 名称 = `  空白边界测试  ` | `errno:0 成功` | 入库保留首尾空格 | ❌ **Bug-4** |
| I | 名称 = `空白边界测试`（无空格） | `errno:0 成功` | **与 H 并存** | ❌ **Bug-4** |
| J | 名称 = 纯数字 `123456` | `errno:0 成功` | 正常 | ✅ 通过 |

**附带发现**：初始数据里已存在一个名称为空格的商品（`id=1181002, goods_sn=1000111`）——系统初始数据本身就带脏数据。

### 4.2 单变量对照实验：价格和库存到底谁有校验

上一版 C 行把两个变量混在一起了，这里拆开重测（2026-09-18 补测）：

| 编号 | 专柜价 | 当前价 | 库存 | 接口返回 | 落库结果 | 判定 |
|---|---|---|---|---|---|---|
| S1 | 10 | 10 | **-5** | `errno:401 参数不对` | 未入库 | ✅ **库存有校验** |
| S2 | 10 | 10 | 0 | `errno:0 成功` | 库存 0 | ✅ 通过 |
| S3 | 10 | **-1** | 10 | `errno:0 成功` | **当前价 -1.00** | ❌ **Bug-5** |
| S4 | **-1** | 10 | 10 | `errno:0 成功` | **专柜价 -1.00** | ❌ **Bug-5** |
| S5 | 10 | 0 | 10 | `errno:0 成功` | 当前价 0.00 | ⚠️ 待确认 |

**结论**：负库存被拦住了，**负价格（当前价、专柜价两个字段）完全放行**。

**用户侧实证**：同学在后台界面亲手新增的「手机」商品，`id=1181009`，`counter_price = -1.00`，已入库。说明**界面路径同样能复现**，不是只有接口才有的现象。

**依据（为什么这是 Bug）**：
- 前端：`create.vue` 第 13-16 行，专柜价格用的是普通 `<el-input>`，**没有任何 min 限制、没有 type=number、没有 rules 校验**
- 后端：`AdminGoodsService` 只做商品名查重，不校验价格
- 数据库：`retail_price` / `counter_price` 为 `decimal(10,2)`，可存负数，无 CHECK 约束
- 业务常识：价格不能为负（**依据属于第 4 层，提 Bug 时注明"需求未明确，建议"**）

## 五、可提交的 5 个 Bug（可直接复制进禅道）

### Bug-1【严重】商品编号可重复，无唯一性校验

```
【所属模块】商品管理-新增商品
【严重程度】严重   【优先级】高

【前置条件】admin123 已登录后台 http://localhost:9527

【复现步骤】
1. 商品管理 → 商品列表 → 添加
2. 商品编号填 T001，名称填"测试商品A"，提交 → 成功
3. 再次点添加，商品编号仍填 T001，名称填"测试商品B"，提交

【预期结果】
提示"商品编号已存在"，不允许保存（商品编号作为业务唯一标识，应唯一）

【实际结果】
两次均保存成功。数据库执行
SELECT id,goods_sn,name FROM litemall_goods WHERE goods_sn='T001';
返回两条记录 id=1181003、1181004，goods_sn 均为 T001

【依据】
需求未明确，但 litemall_goods.goods_sn 为商品业务编号（NOT NULL 且有索引），
按业务常识应唯一；后端 AdminGoodsService 仅对 name 做查重，未对 goods_sn 查重。

【附件】两条记录的查询结果截图
```

### Bug-2【一般】商品名称超长导致 502 系统内部错误

```
【复现步骤】
1. 商品管理 → 添加
2. 商品名称输入 200 个字符（例如 200 个"测"），其余字段正常
3. 提交

【预期结果】
前端限制输入长度或提示"商品名称不能超过 127 个字符"，提交时给出友好提示

【实际结果】
弹出"业务错误：系统内部错误"（errno 502），用户无法知道错在哪里

【依据】
数据库 litemall_goods.name 为 varchar(127)，MySQL sql_mode 含 STRICT_TRANS_TABLES，
超长写入抛异常且未被捕获转换为友好提示；前端 rules 未配置 max 长度限制。

【附件】报错弹窗截图
```

### Bug-3【一般】商品名称仅含空白字符可保存成功

```
【复现步骤】
1. 商品管理 → 添加
2. 商品名称输入一个制表符（Tab 键）或全角空格
3. 提交

【预期结果】
提示"商品名称不能为空"（trim 后为空应视为空）

【实际结果】
保存成功，数据库 litemall_goods 中该记录 name 字段为一个制表符

【补充】
名称输入单个半角空格时，提示"商品名已经存在"（errno 611），
而实际期望提示是"名称不能为空" —— 提示与实际不符，误导用户。
原因：初始数据中已存在 name 为空格的商品（id=1181002）。

【依据】
前端 required 校验不 trim 空白字符；后端仅做重名判断，不做空白校验。
```

### Bug-4【一般】商品名称首尾空格未 trim，导致重名商品可并存

```
【复现步骤】
1. 新增商品，名称填 "  空白边界测试  "（前后各两个空格）→ 保存成功
2. 再新增商品，名称填 "空白边界测试"（无空格）→ 保存成功

【预期结果】
第 2 步应提示"商品名已经存在"（两者 trim 后同名）

【实际结果】
两条都保存成功，数据库中同时存在 id=1181006 和 id=1181007，名称实质相同

【依据】
后端 AdminGoodsService 使用 andNameEqualTo(name) 直接比对，未做 trim 处理；
MySQL 默认比较会忽略尾部空格但不忽略前导空格，导致首尾带空格的名称可绕过查重。
```

```

【前置条件】admin123 已登录后台 http://localhost:9527

【复现步骤】
1. 商品管理 → 商品列表 → 添加
2. 商品编号填 1102913，名称填"手机"
3. 专柜价格填 -1，当前价格填 0，其余默认
4. 点击上架/确定

【预期结果】

【实际结果】
```

## 七、这套方法怎么复用到其他模块

照着这个套路，你可以自己去挖别的模块（品牌、类目、优惠券、订单……）：

1. 打开对应页面的 `.vue` 文件 → 看 `rules` → **知道前端校验了什么**
2. 打开对应的 `Admin*Controller.java` → 看有没有 `@NotNull/@Valid` → **知道后端校验了什么**
3. `DESC 表名` → **知道数据库能存什么**
4. 三者对不上、或者都缺失但业务上不合理的地方 → **就是 Bug 候选**
