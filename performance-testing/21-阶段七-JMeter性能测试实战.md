## 三、GUI 界面地图（第一次打开就照这个认）

```
┌─────────────────────────────────────────────────────┐
│ 菜单栏  文件 编辑 搜索 运行 选项 帮助                 │
├──────────────────┬──────────────────────────────────┤
│ ① 测试计划树      │  ③ 右侧：你选中元素的详细设置      │
│  (左栏)          │                                  │
│ Test Plan        │  ┌ 线程组 → 线程数/Ramp-up/循环    │
│  └ 线程组         │  └ HTTP请求 → 服务器/IP、路径、方法 │
│     ├ HTTP请求    │                                  │
│     ├ HTTP请求    │                                  │
│     └ 监听器      │                                  │
├──────────────────┴──────────────────────────────────┤
│ ② 工具栏：绿色 ▶ 启动 | 停止 | 清除结果 | 保存       │
└─────────────────────────────────────────────────────┘
```

**六个必认元素**（JMeter 的思维模型就这六个）：

| # | 元素 | 角色 | 类比 |
|:--:|---|---|---|
| 1 | **测试计划** | 最外层容器 | 一个项目 |
| 2 | **线程组** | 模拟"多少个用户" | 一个班级 |
| 3 | **取样器**（HTTP 请求） | 真正发出的请求 | 一次点击 |
| 4 | **配置元件**（HTTP 请求默认值 / 请求头管理器） | 公共设置 | 统一的地址簿 |
| 5 | **断言** | 判断对错 | 判卷老师 |
| 6 | **监听器**（聚合报告 / 察看结果树） | 收结果 | 统计员 |

> ⚠️ **压测时务必关掉「察看结果树」**：它会把每个响应全文存进内存，跑 5000 次请求能把你 2 GB 可用内存直接吃干。我建的测试计划里它默认就是关的。

## 四、三个核心概念（面试必问）

### ① 线程组三要素

| 参数 | 含义 | 怎么设 |
|---|---|---|
| **线程数** | 并发用户数 | 想模拟 50 个用户同时操作就填 50 |
| **Ramp-up**（爬坡） | 多少秒内把线程**逐渐**启动完 | 填 50 而线程数是 50 → 每秒起 1 个。**不要填 0**（瞬间起 50 个，等于用尖峰压人家） |
| **循环次数** | 每个线程重复几轮 | 冒烟用 1，压测用固定时长（见第七节） |

### ② 关联（Correlation）——性能测试的命门

litemall 的商品列表接口要 header `X-Litemall-Admin-Token`，而这个 token 是**登录返回的、每次都不同**。

**处理办法：JSON 提取器**（在登录请求下加）：

| 字段 | 值 |
|---|---|
| Names of created variables | `token` |
| JSON Path expressions | `$.data.token` |
| Match No. | `1`（取第一个） |
| Default Values | `TOKEN_NOT_FOUND`（取不到时的兜底，**方便排查，不要留空**） |

之后在商品列表接口的请求头里写 `X-Litemall-Admin-Token` = `${token}`。

> **为什么必须有 Default Values**：如果留空，取不到就是个空字符串，JMeter 会带着空 header 继续跑，你会看到一堆 501 却不知道为什么。填 `TOKEN_NOT_FOUND` 一眼就知道是提取失败。

### ③ 四个核心指标（报告里只写这四个）

| 指标 | 含义 | 看什么 |
|---|---|---|
| **TPS**（吞吐量） | 每秒处理多少笔事务 | **只升不降才是好**；加并发 TPS 不涨 = 到瓶颈了 |
| **平均响应时间** | 平均多久返回 | 行业经验：< 1 s 可接受，> 3 s 用户明显烦躁 |
| **90% Line** | 90% 的请求都快于这个值 | 比平均值更真实 —— **平均值会被少数快请求掩盖** |
| **错误率** | 失败请求占比 | 压测要求 **0%**；一出现就要停下来查 |

### 第 1 步：先看看脚本长什么样（GUI）

双击 `工具\apache-jmeter-5.6.3\bin\jmeter.bat` → 菜单 `File → Open` → 选
`性能测试\scripts\litemall-admin-core.jmx`

展开左侧的树，你会看到：

```
litemall 后台核心链路压测
├── HTTP请求默认值              ← 服务器 127.0.0.1、端口 8080 写在这里，改一处全局生效
└── 压测线程组
    └── 事务-登录并查询商品列表   ← 事务控制器：把 2 个请求算成 1 笔业务
        ├── 01 POST 登录 /admin/auth/login
        │   ├── 请求头 Content-Type=application/json
        │   ├── 关联-提取 token
        │   └── 断言-登录成功 errno=0
        └── 02 GET 商品列表 /admin/goods/list
            ├── 请求头 X-Litemall-Admin-Token=${token}
            ├── 断言-查询成功 errno=0
            └── 断言-响应时间小于 2000ms
```

**为什么要用「事务控制器」**：一场业务是"登录 + 查列表"两笔 HTTP，但用户感知的是**一个动作**。事务控制器把它算成一笔，报表里才能看到"用户完成一次操作要多久"。勾选 `Generate parent sample` 后，报告里会出现 `事务-登录并查询商品列表` 这一行。

## 七、实测结果与瓶颈判断（本节是全文核心）

### 7.1 先看一个"坑"：循环模式的 TPS 不能信

用「循环 10 次」的脚本跑 10/30/50/100 并发，得到：

| 并发 | 事务 TPS | 平均响应 |
|---|---|---|
| 10 | 18.6 | 121 ms |
| 30 | 50.4 | 162 ms |
| 50 | 47.2 | 101 ms |
| 100 | 92.0 | 136 ms |

看上去"100 并发有 92 TPS"，但**这是假的**。手算一遍：

```
10 并发：100 次请求 ÷（5 秒爬坡 + 1.2 秒执行）≈ 16 TPS   ← 实测 18.6
100 并发：1000 次请求 ÷（10 秒爬坡 + 1.4 秒执行）≈ 88 TPS ← 实测 92.0
```

**完全吻合。** 说明这个数字测的是**请求到达率**，不是系统的**处理能力** —— 分母里那一大坨"爬坡时间"把 TPS 稀释了。

> 🔑 **结论：要测容量，必须让压测跑得足够久、久到爬坡可以忽略。** 这就是稳态压测存在的理由。

### 7.2 稳态压测（固定时长 45 秒）——这才是真数据

| 并发 | 事务 TPS | 平均响应 | 90% 线 | 最大 | 登录接口平均 | 商品列表平均 | 错误率 |
|:--:|---|---|---|---|---|---|---|
| **20** | **95.2** | **199 ms** | 253 ms | 486 ms | 181 ms | 18 ms | **0%** |
| **50** | **94.7** | **471 ms** | 708 ms | 2033 ms | 388 ms | 84 ms | **0%** |
| **100** | **119.1** | **750 ms** | 1046 ms | 3423 ms | 538 ms | 214 ms | **0%** |

### 7.3 拐点判断：瓶颈出现在 **20 并发附近**

把三档连起来读，规律非常清楚：

| 观察 | 数值 | 说明 |
|---|---|---|
| 并发 20 → 50 | **TPS 95.2 → 94.7（+0%）** | 加了一倍多的人，**吞吐一点没涨** |
| 并发 20 → 50 | **响应 199 → 471 ms（×2.4）** | 多出来的人全在**排队** |
| 并发 50 → 100 | TPS 94.7 → 119.1（+26%） | 边际收益极低 |
| 并发 50 → 100 | 响应 471 → 750 ms（×1.6） | 延迟继续线性恶化 |
| 全程 | **错误率 0%** | 系统没崩，是**"慢"不是"挂"** |

用**利特尔法则**（并发 = TPS × 响应时间，反过来 容量 = 并发 ÷ 平均响应时间）验算：

```
20 并发  ÷ 0.199 s ≈ 100 TPS
50 并发  ÷ 0.471 s ≈ 106 TPS
100 并发 ÷ 0.750 s ≈ 133 TPS
```

三档都指向同一个天花板：**约 100~130 TPS**。

**结论**：

1. 系统吞吐上限 ≈ **100~130 TPS**，从 **20 并发起就已进入饱和区**；
2. 20 并发 = 舒适区（响应 199 ms）；50 并发以上只是把延迟从 0.2 秒推到 0.75 秒，**用户体验断崖式下降而吞吐没涨**；
3. **登录接口是主要瓶颈点**：它占单笔事务耗时的 90%+（181 ms vs 18 ms），并发升高后从 181 ms 涨到 538 ms，是延迟放大的主源。

### 7.4 附加实验：一个参数能让吞吐腰斩（把老 Bug 升级成性能问题）

20 并发、45 秒，**只改 `limit` 一个值**：

| 指标（商品列表） | `limit=20` | `limit=0` | 变化 |
|---|---|---|---|
| 吞吐 TPS | 98.1 | **42.6** | **↓ 56.6%** |
| 平均响应 | 15.7 ms | **288.5 ms** | **↑ 1738%** |
| 平均响应体 | 53.3 KB | **1480.8 KB** | **↑ 2678%（27.8 倍）** |
| 错误率 | 0% | 0% | — |

这就是前面 Fiddler 那个 **Bug-8（禅道 #4）** 的**性能侧面**：

> 一个普通用户改一个数字，就能让单次查询数据量放大 27.8 倍，在 20 人同时用的负载下把**查询吞吐砍掉一半以上**。

**交叉验证**：Fiddler 抓到的单次响应体 **1,514,715 字节 ≈ 1479 KB**，与 JMeter 实测均值 **1480.8 KB** 几乎一致 —— 两条独立取证路径互相印证。

**这就是"同一个缺陷，换一个视角"**：功能测试说它"违反参数校验"，性能测试说它"能被低成本地用来拖垮系统"。**不是新 Bug，不要新开单**，而是把这份数据补进 #4 的证据里。

### 7.5 为什么登录这么慢？（顺带一个反直觉的知识点）

不是因为代码写得烂，而是因为**密码校验故意做得慢**：后台用户密码用 **BCrypt** 存储（你在 Bug-9 里就见过 `/admin/user/list` 返回的 `$2a$10$...` 哈希）。BCrypt 的设计目标就是**每次校验都消耗几十~几百毫秒 CPU**，让暴力破解变得不划算。

> 所以这是**安全特性，不是缺陷**。写报告时千万不要把它当 Bug 提 —— 那会暴露你没读懂设计。

**真要优化，方向是"少登录"而不是"改快算法"**：真实业务里 nobody 每次查询都重新登录，都是登录一次拿 token 复用。这可以直接转成一条性能优化建议。

## 八、踩坑表（我实跑时踩到的，都给你标出来）

| # | 现象 | 真因 | 正确做法 |
|:--:|---|---|---|
| 1 | 命令行跑完显示 `summary = 0` | 汇总器的**基线行**，不是失败 | 看 `.jtl` 或报告，别信这行 |
| 2 | `-e -o` 报错 | 输出目录**必须为空或不存在** | 每次换新目录，或先删旧的 |
| 3 | 找不到 java | `JAVA_HOME` 没生效 | 跑前设 `$env:JAVA_HOME = "D:\jdk-11"` |
| 4 | 一堆 `plugin scanning deprecated` WARN | log4j 提示 | 无视 |
| 5 | 加并发 TPS 不涨、响应翻倍 | **到瓶颈了** —— 这是结论不是 bug | 记下来，写进报告的瓶颈章节 |
| 6 | 压测时机器卡死 | JMeter 和被测服务**在同一台机器**抢 CPU/内存 | 见第十节"局限声明" |
| 7 | 察看结果树开着跑压测 → 内存爆 | 它缓存所有响应全文 | **压测前关闭** |
| 8 | 501 未登录一大堆 | token 没提取到（关联失败） | 给 JSON 提取器填 Default Values |
| 9 | **秒退、0 采样，但退出码是 0** | 报告目录非空；**JMeter 失败时退出码照样是 0** | 判成功要看 `.jtl` 有没有数据，别只看退出码 |
| 10 | 删了报告目录却还报"folder is not empty" | `Remove-Item` / `rmtree` **可能静默失败** | 删完要**复查**；复查还在就换个唯一目录名 |
| 11 | **`NumberFormatException: For input string: "$var"`** | PowerShell 里 `-Jxxx=$var` **不加引号不展开变量** | 写成 `"-Jxxx=$var"`（见下） |

### 关于第 11 条（这个坑最阴，务必记住）

**受控实验**（用 node 打印真实收到的参数）：

```
& $node $s -Jlimit=$x    →  实收 ["-Jlimit=$x"]   ❌ 字面量，变量没展开
& $node $s "-Jlimit=$x"  →  实收 ["-Jlimit=20"]   ✅
```

**规律**：PowerShell 里**以 `-` 开头的 token 被当作"参数名"整体透传，不做变量展开**。值里是字面量数字（`-Jthreads=2`）时看不出问题，**一旦带变量就静默传错**。

**我踩它的后果**：JMeter 把 `limit=$lim` 原样发给服务端 → 服务端 `NumberFormatException` → 返回异常体 → 断言正确判失败 → 整轮压测 100% 错误、**结果全部作废**。

> 🔑 **由此得到一条更重要的纪律**：
> **断言失败时，第一步不是写 Bug 单，而是分辨"脚本错"还是"服务端错"。**
> 唯一可靠手段是看服务端日志：`docker logs --tail 50 litemall`。
> 我这次差点就交出一份"系统在 20 并发下 100% 失败"的假报告。

## 九、面试怎么说（3 句话版本）

> "我在 litemall 项目上做过一轮性能压测。用 JMeter 搭了'登录 + 商品列表'的核心链路脚本，用 JSON 提取器做 token 关联，加了响应断言和响应时间断言。**先做梯度加压，发现短时循环压测的 TPS 会被爬坡时间稀释**，于是改成 45 秒固定时长的稳态压测。结果是系统吞吐天花板大约 100~130 TPS，**并发从 20 加到 50 时 TPS 完全没涨、响应时间翻了 2.4 倍**，说明 20 并发就进入饱和区了；进一步定位到瓶颈主要在登录接口，因为它用了 BCrypt 做密码校验，本身是慢操作。**全场景错误率 0%，系统是慢而不是挂。**"

**如果被追问"你怎么判断到瓶颈了"**，标准答案三条：

1. **TPS 不再随并发上升**（加人不出活）
2. **响应时间随并发线性上涨**（多出来的人都在排队）
3. **错误率开始抬头 / 响应时间曲线持续上扬**（再压就要出错了）

## 十、必须写进报告的"局限声明"（不加会显得不专业）

> 本次压测中 **JMeter（压测客户端）与被测服务部署在同一台物理机**，两者共享 CPU 与内存。因此测得的容量数字**低于真实部署环境的水平**，结论应作为**相对趋势判断**（拐点位置、瓶颈接口）使用，不宜直接作为生产容量规划依据。
> 更严谨的做法：压测机与被测机分离，并监控服务端 CPU/内存/数据库连接数。
