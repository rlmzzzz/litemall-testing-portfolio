> 生成时间：2026-09-18

## 零、先说为什么非查数据库不可

界面上显示"保存成功"，**不等于数据真的存对了**。三种典型翻车：

| 现象 | 界面 | 数据库 |
|---|---|---|
| 数据存错字段 | 无异常 | 价格存进了 `counter_price` 而不是 `retail_price` |
| 数据没删干净 | 列表里没了 | `deleted` 只是标记成 1，记录还在 |
| 关联表没同步 | 商品列表正常 | `litemall_goods_product` 库存还是 0 |

**只点界面不查库的测试，面试官一听就知道是"点点点"。** 界面 + 接口 + 数据库三方核对，才是完整的功能测试。

## 一、怎么连上数据库（三种方式，选一个）

### ⚠️ 先记住这个坑

**不要用图形化工具连 `localhost:3307`。** 你本机禅道的 MySQL 也抢了这个端口，连上去看到的是禅道的数据，不是 litemall。

正确姿势是**从容器内部连**，绕开端口。

---

### 方式 A：一行式查询（最推荐，复制即用）

打开 **PowerShell**，粘贴：

```powershell
docker exec mysql mysql --default-character-set=utf8mb4 -uroot -plitemall123456 litemall -e "SELECT id,goods_sn,name,retail_price,counter_price,is_on_sale FROM litemall_goods ORDER BY id DESC LIMIT 5;"
```

| 参数 | 含义 |
|---|---|
| `docker exec mysql` | 进名为 mysql 的容器 |
| `--default-character-set=utf8mb4` | **防中文乱码，必须带** |
| `-uroot` | 用户名 root |
| `-plitemall123456` | 密码（-p 后无空格） |
| `litemall` | 库名 |
| `-e "SQL语句"` | 执行完就退出 |

**优点**：一条命令出结果，适合查一次。
**缺点**：SQL 里有双引号时要改成单引号。

---

### 方式 B：交互式（连续查多条时用这个）

```powershell
docker exec -it mysql mysql --default-character-set=utf8mb4 -uroot -plitemall123456 litemall
```

进去后提示符变成 `mysql>`，可以一直敲 SQL，**每条结尾必须加分号**：

```sql
mysql> SELECT COUNT(*) FROM litemall_goods;
mysql> DESC litemall_goods;
mysql> exit
```

> 如果卡住不动，按 `Ctrl + C` 退出重来。

---

### 方式 C：图形化工具（Navicat / DataGrip）

想用的话，**必须先把端口冲突解决掉**。两个办法：

**办法 1（推荐）：改 litemall 的映射端口**

编辑 `D:\litemall\litemall-master\docker\docker-compose.yml`，把 MySQL 那段改成 `3310:3306`，然后 `docker compose up -d`。之后用 `localhost:3310` 连。

**办法 2：用 SSH 隧道之类的方式绕开**（新手不推荐）

连接参数：

| 项 | 值 |
|---|---|
| 主机 | `localhost` |
| 端口 | `3310`（改过之后） |
| 用户名 | `root` |
| 密码 | `litemall123456` |
| 数据库 | `litemall` |

## 二、中文乱码怎么办

**症状**：查出来是 `??2`、`??????`。

**原因**：Windows 终端默认 GBK，MySQL 返回的是 UTF-8。

**解决**：命令里加 `--default-character-set=utf8mb4`。上面所有命令都带了。

**还不行的话**，在 PowerShell 里先敲一条再查：

```powershell
chcp 65001
```

（把终端代码页切成 UTF-8）

## 三、表结构速查

| 表名 | 存什么 | 测试时用来 |
|---|---|---|
| `litemall_goods` | 商品主表（名称/编号/价格/上下架） | **校验新增、编辑、上下架** |
| `litemall_goods_product` | 货品表（规格/**库存**） | **校验库存扣减** |
| `litemall_goods_specification` | 规格表 | 校验规格增删 |
| `litemall_goods_attribute` | 参数表 | 校验商品参数 |
| `litemall_order` | 订单主表 | 校验下单、金额 |
| `litemall_order_goods` | 订单商品明细 | 校验订单与商品关联 |
| `litemall_user` | 前台用户 | 校验注册 |
| `litemall_admin` | 后台管理员 | 校验账号权限 |
| `litemall_permission` | 权限清单 | 校验越权 |
| `litemall_category` | 类目 | 校验类目增删 |
| `litemall_brand` | 品牌商 | 校验品牌增删 |
| `litemall_log` | 操作日志 | **看后台操作有没有留痕** |

### `litemall_goods` 关键字段

```
id                int        主键，自增
goods_sn          varchar(63) 商品编号（NOT NULL，有索引但非唯一）
name              varchar(127) 商品名称（NOT NULL）
category_id       int        类目
brand_id          int        品牌
is_on_sale        tinyint    是否上架：1=上架 0=下架
is_new / is_hot   tinyint    新品 / 热卖
sort_order        smallint   排序
unit              varchar    单位（如"件"）
counter_price     decimal    专柜价（划线价）
retail_price      decimal    当前价（实售价）
add_time          datetime   创建时间
update_time       datetime   更新时间
deleted           tinyint    逻辑删除：0=正常 1=已删
```

> ⚠️ `litemall_goods` **没有 stock 字段**！库存在 `litemall_goods_product.number` 里。这是新手最容易踩的坑。

## 四、常用 SQL 清单（复制即用）

### 4.1 商品类

**查最近新增的商品（找你刚创建的）**
```sql
SELECT id, goods_sn, name, retail_price, counter_price, is_on_sale,
       DATE_FORMAT(add_time,'%m-%d %H:%i') AS 创建时间
FROM litemall_goods ORDER BY add_time DESC LIMIT 10;
```

**按名称模糊查**
```sql
SELECT id, goods_sn, name, retail_price, counter_price, is_on_sale
FROM litemall_goods WHERE name LIKE '%手机%';
```

**按编号精确查**
```sql
SELECT * FROM litemall_goods WHERE goods_sn = '1102913';
```

**查商品 + 库存（连表）**
```sql
SELECT g.id, g.name, g.retail_price, p.specifications AS 规格,
       p.price AS 货品价, p.number AS 库存
FROM litemall_goods g
LEFT JOIN litemall_goods_product p ON p.goods_id = g.id AND p.deleted = 0
WHERE g.id = 1181010;
```

**统计上架 / 下架数量**
```sql
SELECT is_on_sale AS 上架状态, COUNT(*) AS 数量
FROM litemall_goods WHERE deleted = 0 GROUP BY is_on_sale;
```

### 4.2 找脏数据（挖 Bug 专用）

**查重复的商品编号**
```sql
SELECT goods_sn, COUNT(*) AS 重复数
FROM litemall_goods GROUP BY goods_sn HAVING COUNT(*) > 1;
```

**查价格为负的商品**
```sql
SELECT id, goods_sn, name, retail_price, counter_price
FROM litemall_goods WHERE retail_price < 0 OR counter_price < 0;
```

**查名称为空白字符的商品**
```sql
SELECT id, goods_sn, name, LENGTH(name) AS 字节长度
FROM litemall_goods WHERE TRIM(name) = '' OR name REGEXP '^[[:space:]]+$';
```

**查库存为负的货品**
```sql
SELECT p.id, p.goods_id, g.name, p.number
FROM litemall_goods_product p
LEFT JOIN litemall_goods g ON g.id = p.goods_id
WHERE p.number < 0;
```

### 4.3 账号与权限

**查管理员账号和角色**
```sql
SELECT id, username, role_ids, last_login_time FROM litemall_admin;
```

**查操作日志（验证后台操作有没有留痕）**
```sql
SELECT id, admin, ip, type, action,
       DATE_FORMAT(add_time,'%m-%d %H:%i:%s') AS 时间
FROM litemall_log ORDER BY add_time DESC LIMIT 20;
```

### 4.4 系统信息

```sql
SELECT @@sql_mode;          -- 严格模式（决定超长/非法值是报错还是截断）
SELECT VERSION();           -- MySQL 版本：5.7.44
SELECT DATABASE();          -- 当前库
SHOW TABLES;                -- 所有表
DESC litemall_goods;        -- 表结构
```

## 五、你的实际案例：刚上架的商品怎么查

你在后台新增了"手机"和"手机2"两条，数据库里是这样查到的：

```sql
SELECT id, goods_sn, name, retail_price AS 当前价, counter_price AS 专柜价,
       is_on_sale AS 上架, is_new AS 新品, unit AS 单位,
       DATE_FORMAT(add_time,'%Y-%m-%d %H:%i:%s') AS 创建时间, deleted
FROM litemall_goods ORDER BY add_time DESC LIMIT 6;
```

**实际返回结果：**

| id | 商品编号 | 名称 | 当前价 | 专柜价 | 上架 | 创建时间 |
|---|---|---|---|---|---|---|
| 1181010 | 1181009 | 手机2 | 0.00 | 100.00 | 1 | 2026-09-18 11:30:59 |
| 1181009 | 1102913 | 手机 | 0.00 | **-1.00** | 1 | 2026-09-18 11:26:27 |

**怎么读懂这张表：**

- `is_on_sale = 1` → 确实上架成功了，界面和数据库一致 ✅
- `add_time` → 你自己创建的时间，用这个能认出哪些是你的测试数据
- `retail_price = 0.00` → 你没填当前价，默认存了 0
- **`counter_price = -1.00`** → 专柜价存了个负数 ❌ **这是个 Bug**

## 六、数据校验的标准套路（以后所有模块都这么干）

不要只查一次。**操作前查 → 操作 → 操作后查 → 对比**，四步：

```sql
-- 第 1 步：操作前（记录基线）
SELECT id, name, retail_price, is_on_sale FROM litemall_goods WHERE id = 1181010;

-- 第 2 步：在界面上做操作（比如改成下架）

-- 第 3 步：操作后（看变化）
SELECT id, name, retail_price, is_on_sale FROM litemall_goods WHERE id = 1181010;

-- 第 4 步：对比，判断是否符合预期
```

**截图时把这三样放一起**：操作前查询结果 + 界面操作 + 操作后查询结果。贴进 Bug 单，开发无法抵赖。

> 面试加分说法：*"我测数据一致性时，会在操作前后各查一次数据库做对比，而不是只看界面返回结果。"*

## 七、踩过的坑（别再踩）

| 坑 | 现象 | 解法 |
|---|---|---|
| 连错库 | 连 `3307` 看到禅道的数据 | 用 `docker exec` 从容器内连，不用宿主端口 |
| 中文乱码 | 显示 `??2` | 加 `--default-character-set=utf8mb4` |
| 找不到库存字段 | `Unknown column 'stock'` | 库存在 `litemall_goods_product.number`，不在 goods 表 |
| 查不到刚建的商品 | 结果为空 | 加 `deleted = 0` 条件；或按 `add_time` 倒序找 |
| 删了还能查到 | 记录还在 | 是**逻辑删除**，`deleted` 字段变 1，不是真删 |
| PowerShell 吞掉分号 | SQL 只执行了前半段 | SQL 整体用双引号包起来 |
| 行数对不上 | `information_schema` 显示 204，实际 249 | 那是估算值，以 `SELECT COUNT(*)` 为准 |

## 九、我既没下载 MySQL，也没配过连接，为什么能查？

**因为 MySQL 不在你电脑上，它在 Docker 容器里。**

### 你电脑上其实有两个 MySQL

| | 位置 | 版本 | 里面有什么 |
|---|---|---|---|
| 你本机装的 | `D:\MySQL\MySQL Server 8.0\bin\mysql.exe` | **8.0.40**（Windows 版） | 跟 litemall 无关 |
| **容器里跑的** | Docker 容器内部 | **5.7.44**（Linux 版） | **litemall 库在这里** |

### 容器到底是什么

容器可以理解为**一台迷你的小电脑**。实测这个容器的系统：

```powershell
docker exec mysql cat /etc/os-release
```

返回：

```
NAME="Oracle Linux Server"
VERSION="7.9"
```

**Oracle Linux 7.9** —— 一个完整的 Linux 操作系统，MySQL 5.7.44 就预装在这个系统里。

它哪来的？回想最开始那一步：

```powershell
docker pull mysql:5.7
```

`docker pull` 拉下来的**不是空壳**，是别人做好的、装好了 MySQL 的整个系统快照。所以：

> 你没装 MySQL，是 **pull 镜像的时候把它整套带来了**。

### 一条命令里出现两次 mysql，含义完全不同

```powershell
docker exec mysql  mysql -uroot -plitemall123456 litemall -e "SELECT ..."
           ↑             ↑
      容器名字      容器内部的 mysql 客户端程序
```

- 前半截 `docker exec mysql` = **进入名叫 mysql 的容器**
- 后半截 = 在容器**里面**执行 mysql 命令

相当于：你走到那台小电脑前，用**它自己的** MySQL 查**它自己硬盘上**的数据。跟你的 Windows 没关系。

### 为什么 Navicat 连不上

容器是**隔离**的，外面默认碰不到。`docker-compose.yml` 写了 `3307:3306`，本来要把容器的 3306 暴露到你电脑的 3307——**但 3307 被你本机禅道的 MySQL 抢了**，litemall 容器没抢到。

所以必须用 `docker exec` 从**内部**连，绕开端口冲突。

### 眼见为实的两条命令

```powershell
# ① 容器里有哪些库 → 能看到 litemall
docker exec mysql mysql -uroot -plitemall123456 -e "SHOW DATABASES;"
```

```
information_schema / litemall / mysql / performance_schema / sys
```

```powershell
# ② 本机客户端连 3307 → 只有 zentao，没有 litemall
mysql -h127.0.0.1 -P3307 -uroot -p123456 -e "SHOW DATABASES;"
```

```
information_schema / mysql / performance_schema / zentao
```

两个结果一对比就全明白了。

### 这也是可以讲给面试官听的点

> *"被测系统是 Docker Compose 起的三个容器，数据库跑在独立的 MySQL 5.7 容器里。因为宿主 3307 端口被占用，我改用 `docker exec` 进容器内部查询，做界面与数据库的一致性校验。"*

比说"我连不上数据库"强得多。
