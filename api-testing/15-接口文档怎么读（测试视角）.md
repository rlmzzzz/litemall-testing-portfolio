## 2. 核心方法：一个接口，测试只看 5 块

文档第 1.6 节定义了每个接口的写法（作者自己定的模板）：

```
应用场景   ← 这个接口是干嘛的
接口链接   ← 地址 + 方法
请求参数   ← 能传什么
响应内容   ← 返回什么
错误码     ← 会报哪些错
```

作为测试，你在这 5 块里**只盯 5 样东西**：

| # | 看什么 | 在文档哪一块 | 为什么测试要看 |
|---|---|---|---|
| ① | **地址 + 方法** | 接口链接 | 写错一个字符就 404，方法错就 405 |
| ② | **哪些参数必填、什么类型、什么范围** | 请求参数 | **用例设计的主战场**（边界值、等价类全靠它） |
| ③ | **返回结构（字段名、嵌套层级）** | 响应内容 | 写断言必须知道字段叫什么、在哪一层 |
| ④ | **错误码含义** | 错误码 | **判断"异常场景对不对"的唯一依据** |
| ⑤ | **鉴权方式** | 1.4 Token 节 | 决定了请求头怎么配 |

## 3. 拿真实接口走一遍

用文档 2.4.1「商品列表」做例子（原文我从文档里摘出来了）：

```
应用场景
    商品列表

接口链接
    GET /wx/goods/list

请求参数
    isNew: 是否新品，true或者false
    isHot: 是否热卖商品，true或者false
    keyword: 关键字，如果设置则查询是否匹配关键字
    brandId: 品牌商ID，如果设置则查询品牌商所属商品
    categoryId: 商品分类ID，如果设置则查询分类所属商品
    page: 请求页码
    limit: 每一页数量
    sort: 排序字段
    order: 升序降序
```

### 看完这 4 行，"内行"会立刻问出这些问题

| 文档写的 | 你该追问的 | 追问出来的测试用例 |
|---|---|---|
| `GET /wx/goods/list` | 方法确定是 GET，参数在 URL 后 | — |
| `isNew: true 或 false` | 传 `1` / `是` / 空 行不行？ | 参数值非法场景 → 预期 errno=402 |
| `keyword: 关键字` | 传不存在的关键字返回空数组还是报错？ | 查询无结果场景 |
| `brandId: 品牌商ID` | 传一个不存在的 ID 呢？ | 数据不存在场景 |
| `page: 请求页码` | **传 0、-1、abc 呢？**（1.1.3 只说"从 1 开始"） | 边界值 → **你的 Bug-8 就是这么来的** |
| `limit: 每一页数量` | **传 0 呢？传 100000 呢？**（文档没说范围！） | 边界值 → **Bug-8 实测返回全量 250 条** |
| `sort / order` | `order` 传 `DESC` 大写呢？传 `乱写` 呢？ | 参数格式场景 |

**看到关键了吗？**

> **文档没写的地方，就是测试的战场。**
>
> 文档说"limit 是每一页数量"，但**没说不能是 0**。开发也就照着"没说就不校验"去实现，结果 `limit=0` 返回了全量 250 条 —— **Bug-8 就是这么被测出来的**。
>
> 这就是为什么"照着文档写用例"只能测出皮毛，**"盯着文档的空白处写用例"才能测出真 Bug。**

## 4. 我把这份文档实测了一遍，发现 6 处问题

下面每一条都是我**真实请求**得到的结果，可以截图提禅道（属于"文档缺陷"，优先级一般，但能体现你的严谨）。

### 4.1 错误码 `506` 文档里根本没有定义

文档 1.3.1 只定义到 `505`：

```
501，验证失败
502，系统内部错误
503，业务不支持
504，更新数据失效
505，更新数据失败
```

我实测（用 mall123 账号访问它没权限的接口）：

| 实测请求 | errno | errmsg |
|---|---|---|
| mall123 → `/admin/goods/list` | **506** | **无操作权限** |
| mall123 → `/admin/user/list` | **506** | **无操作权限** |

**506 = 无操作权限，文档漏了。** 而且这个码非常关键 —— 你之前排查越权 Bug-7 就是靠它。

### 4.2 错误码 `602` 被定义了两次，语义还冲突

文档 1.3.3 原文：

```
* ADMIN_INVALID_NAME = 601
* ADMIN_INVALID_PASSWORD = 602     ← 602 第 1 次
* ADMIN_NAME_EXIST = 602           ← 602 第 2 次（冲突！）
* ADMIN_ALTER_NOT_ALLOWED = 603
```

同一个数字 `602` 既是"密码无效"又是"名称已存在"。**调用方拿到 602 根本不知道该提示哪个。**

### 4.3 文档 1.4.3 的示例路径写错了

文档 1.4.3（管理后台 token）第 283 行：

```
GET http://localhost:8080/wx/address/list      ← /wx/ 是前台路径
X-Litemall-Admin-Token: f2dbcae8-...           ← 却配了后台的 token
```

对比 1.4.2（商场 token）第 251 行，用的是同一个路径 `/wx/address/list` 配 `X-Litemall-Token`（这是对的）。

**结论：1.4.3 的示例是从 1.4.2 复制粘贴过来的，头改了、路径忘改。** 照着这个示例去测，会一脸茫然。

### 4.4 Token 有效期：文档一个字没提，而且两端不一样

文档 1.4 只说"用 token 验证权限"，**完全没写有效期**。我实测挖出来了：

| 端 | token 格式 | 有效期 | 证据来源 |
|---|---|---|---|
| 管理后台 `/admin/` | **UUID**（如 `4b4e93b5-bde2-471a-b4cd-4e607c85075b`） | **6 小时** | 源码 `AdminWebSessionManager.java:20` → `setGlobalSessionTimeout(MILLIS_PER_HOUR * 6)` |
| 前台 `/wx/` | **JWT**（三段式，228 位） | **2 小时** | 实测解码 payload：`exp - iat = 7200 秒` |

**前台 JWT 实测解码结果**：

```json
{"alg":"HS256","typ":"JWT"}
{"sub":"this is litemall token","aud":"MINIAPP","iss":"LITEMALL",
 "exp":1789810789,"userId":1,"iat":1789803589}
```

`iat` = 2026-09-19 15:39:49（签发），`exp` = 17:39:49（过期），**正好 2 小时**。

> **这解释了之前那个谜团**：你手上那个浏览器 token 为什么 3.5 小时就失效了？
> 因为**后台是 6 小时**没错，但你如果拿的是**前台 token（2 小时）**，那早就过期了。
> 两端机制完全不同，这也是文档没告诉你的。

### 4.5 文档说 Swagger 能访问，我实测被拒绝

文档 1.11 节说：

```
本地Swagger文档链接：http://localhost:8080/swagger-ui.html
本地swagger-bootstrap-ui文档链接：http://localhost:8080/doc.html
```

我实测三个地址：

| 地址 | HTTP 状态 | 实际返回内容 |
|---|---|---|
| `/swagger-ui.html` | 200 | `You do not have permission to access this page` |
| `/doc.html` | 200 | 同上（仅 46 字节） |
| `/v2/api-docs` | 200 | 同上 |

带上 admin token 再访问，**依然被拒**。

而且注意一个细节：响应的 `Content-Type` 写成了 **`text/palin`** —— **`plain` 拼错了**。这种拼写错误说明这段响应不是成熟框架的默认输出。

> ⚠️ **这条先别急着提 Bug。** 为什么？
> 因为"文档说能访问、实测不能"有两种可能：① 文档过时了；② **我部署时的配置和作者默认的不同**。
> 测试的专业做法是：**先记为"待确认"，排查清楚再定性**。这就是"文档与实际不符"的正确处理流程 —— 不能一看不一致就提 Bug。

（顺便：从**安全角度**看，Swagger 被关掉反而是好事。文档 1.11 自己也警告说"项目一旦需要上线，请及时删除 swagger 依赖，防止接口对外暴露造成安全隐患"。这条**作者的自白**，本身就是一条安全测试的线索。）

## 8. 面试怎么用这些

**被问"你会看接口文档吗"**：

> "会。我一般先看规范章节（请求格式、响应格式、错误码、鉴权），把通用规则建立起来，再按需查具体接口。
>
> 具体到每个接口，我看五处：地址方法、参数约束、返回结构、错误码、鉴权方式。参数约束那部分是我设计边界值用例的主要依据。
>
> 而且我会**校验文档本身**。比如我做的这个 litemall 项目，文档里只覆盖了 41 个前台接口，管理后台接口写的是'略'，所以后台我改用抓包来补。我还发现文档里的错误码表只定义到 505，但实测无权限返回的是 506，这个码没定义；另外 602 这个错误码被重复定义给了两种不同语义。"

**这段的价值**：最后一段"我会校验文档本身"能直接把你和背题的人区分开。**大部分实习生答不出"文档可能是错的"这个认知。**
