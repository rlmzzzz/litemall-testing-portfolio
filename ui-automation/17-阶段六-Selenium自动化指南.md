
### 动作 3：观察导出的文件里 token 是什么值

用记事本打开导出的**环境文件**，找到 `token` 这一行，看它的 `value`：

**你会发现是空的。**

为什么？回想你前天踩的那个坑 —— 环境变量有 **Initial Value / Current Value** 两列：

| 列 | 导出时 |
|---|---|
| Initial Value | ✅ 会被带出去 |
| **Current Value**（你跑出来的真实 token） | ❌ **不会** |

**这个设计是为了防止你的真实 token、密码随文件泄漏出去。**

**但它带来一个必须理解的后果**：别人拿到你的集合 + 环境文件，直接跑**会全部失败**（token 是空的）——除非他**从头跑**，让登录请求先写入新 token。

> 所以你的集合**必须严格遵守"登录排在第一个"**。这就是集合内请求顺序不能乱的原因。

### 筛选标准：什么样的用例值得自动化？

| 特征 | 值得录 | 理由 |
|---|---|---|
| **重复执行频率高** | ✅ | 每次回归都要跑（登录、核心下单流） |
| **业务价值高** | ✅ | 挂了说明系统出大事（冒烟用例） |
| **结果客观可判断** | ✅ | 页面显示的文字/数字能断言，不依赖人工审美 |
| **要反复造数据** | ✅ | 每次回归都要重建数据，最烦人，最该自动化 |
| 页面频繁改版 | ❌ | 脚本天天修，维护成本 > 收益 |
| 一次性的用例 | ❌ | 跑一次就不用了，录它纯浪费 |
| 要人眼看外观 | ❌ | 布局好不好看、颜色对不对，机器判不了 |

### 一句话原则

> **自动化不是"少用手测"，是"把重复劳动交给机器"。**
> 录之前先问自己：**这条用例，我下个月还会不会再跑一遍？** 答案是"不会"，就别录。

## 踩坑预判（提前知道，少走弯路）

**坑 1：litemall 后台是 Vue 单页应用（SPA）**

你之前抓包时见过 `<div id="root"></div>` 是空的 —— 页面内容全靠 JS 动态渲染。

**后果**：你 `open` 一个页面后立刻点按钮，元素**还没渲染出来**，脚本报"元素找不到"。

**解法**：必须加 `waitFor`。**这就是为什么这个项目特别适合练 Selenium** —— 你会被迫理解"等待"这件事。

**坑 2：录出来的脚本很脆**

Selenium IDE 录制时倾向生成带索引的 xpath（`//div[3]/span[2]`），页面一改版就失效。

**解法**：录完要**改造**，换成稳定的定位方式（优先 `id`、其次 `name`、`css` 次之、`xpath` 最后）。

**坑 3：每次跑都要先登录**

自动化跑起来是"全新浏览器"，没有任何登录状态。所以**每条脚本开头都得先登录**。

**解法**：把"登录"录成一个独立脚本，或者用参数化传入账号。
